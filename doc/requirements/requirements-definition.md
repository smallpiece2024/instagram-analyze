## 1. 目的と基本方針

### 1.1 目的

自分の Instagram プロアカウントのデータを Meta 公式 API から継続的に取得して蓄積し、**「どんな投稿が、なぜ伸びたのか」を過去の自分の投稿から学べる分析ツール**を作る。

既存ツールの価値は「API の値を見せること」ではなく、「取得 → 継続保存 → 加工 → 比較 → 意味づけ」にある。両調査の結論は一致している。特に次の 2 点は、今日保存しなければ後から取り戻せない。

- アカウントの日次指標は API で 90 日しか遡れない。ストーリーズは 24 時間で消える。
- 投稿ごとの指標は累計値しか返らない。投稿後にどう伸びたかは、自分で定期的に記録しない限り残らない。

### 1.2 ユーザーの方針（確定事項）

| 項目 | 方針 |
|---|---|
| データ保存 | API の結果を DB に保存する |
| 重点機能 | 動画（リール）の分析を行う |
| DB | Supabase |
| ホスティング | Vercel など、なるべく無料のサービス |
| 開発の進め方 | まず Supabase を Docker で動かし、Web システムもローカルで動く環境を作る |
| リリース | 過剰な機能は作らず、段階的に機能を追加しながらリリースする |

### 1.3 設計原則

1. **データを失わないことを最優先する。** 収集処理は画面より先に作る。画面がなくても収集は止めない。
2. **生データを残す。** API のレスポンスはそのまま保存し、後から指標を計算し直せるようにする。
3. **指標の変更に耐える。** Meta は指標名や定義を頻繁に変える（2025-04 に impressions が views に統一された）。新しい指標をスキーマ変更なしで追加できる構造にする。
4. **定義を明示する。** エンゲージメント率などの率は、分母を画面上で明示する。
5. **Meta 公式 API だけを使う。** スクレイピング、非公式 API、パスワード入力は使わない（規約違反と凍結リスクのため）。
6. **各リリースを小さく保つ。** 1 リリースごとに「動いて役に立つ」状態で区切る。

### 1.4 スコープ外（作らないもの）

- 投稿の予約・公開機能
- コメントへの返信、DM の送受信
- 他人のアカウントの非公開データ（リーチ・保存数・フォロワー一覧など）の推定
- 広告の管理
- 複数ユーザーでの共同利用、権限管理、課金

## 2. 前提と制約

### 2.1 利用者と対象アカウント（仮定）

| 項目 | 仮定 | 確認 |
|---|---|---|
| 利用者 | ユーザー本人 1 名 | 11 章 Q1 |
| 対象アカウント | 本人が管理する Instagram プロアカウント（ビジネスまたはクリエイター）。最初は 1 つ、将来は数個まで | 11 章 Q1 |
| フォロワー数 | 100 人以上 | 11 章 Q1。100 人未満だと属性データや純増データが取れない |
| API の方式 | Facebook Login 方式（Facebook ページとの接続が必要） | 11 章 Q2 |

Facebook Login 方式を仮定した理由は次の 3 点。

- 競合の公開データ取得、ハッシュタグ検索、タグ付け投稿の取得は、この方式でしか使えない。
- ストーリーズのリンククリック数など、この方式でしか取れない指標がある。
- 長期のページアクセストークンは期限がなく、トークン更新の運用が楽になる。

### 2.2 Meta API の主な制約

詳細は Claude 調査の 3 章を参照。要件に直接効くものだけを挙げる。

| 制約 | 内容 | 要件への影響 |
|---|---|---|
| アカウント日次指標の保持期間 | 90 日 | 初回接続時に 90 日分を取り込み、以降は毎日保存する |
| 投稿指標の保持期間 | 2 年、累計値のみ | 投稿後の伸びは定期スナップショットで自前記録する |
| ストーリーズ | 24 時間で取得不能になる | 1 時間ごとに取得する |
| 反映遅延 | 最大 48 時間 | 直近 3 日分は毎日取り直して上書きする |
| レート制限 | 24 時間あたり「4800 × アカウントの表示回数」 | 画面表示のたびに API を呼ばない。収集はスケジュール実行のみ |
| 属性データ | 現在のスナップショットのみ、フォロワー 100 人以上 | 週 1 回保存して推移を作る |
| フォロワー一覧 | API では取得不可 | 対象外 |
| 日本のストーリーズ返信数 | API では常に 0 | 画面に注記する |
| 動画の URL | 有効期限付きの URL | 取得したらすぐ解析する。URL は保存しない |
| 個人アカウント | 対象外 | プロアカウントへの切り替えが前提 |

### 2.3 無料サービスの制約（要確認を含む）

| サービス | 制約 | 影響 |
|---|---|---|
| Supabase Free | DB 500MB、ストレージ 1GB、一定期間アクセスがないとプロジェクトが一時停止する | 容量の見積もりは 8.3 章。定期収集が動いていれば停止しない見込み（未確認） |
| Vercel Hobby | 商用利用不可。Cron は 1 日 1 回まで。関数の実行時間に上限がある | 1 時間ごとの収集や動画解析は Vercel では動かさない。商用利用なら別サービスを検討（11 章 Q4） |
| GitHub Actions | 公開リポジトリは無料。非公開は月 2,000 分まで。スケジュール実行は数分から十数分遅れることがある | 収集ワーカーの定期実行に使う候補。1 時間ごとなら月 720 回程度 |

## 3. リリース計画

各リリースは前のリリースの上に積み上げる。R0〜R3 を最初の目標とし、R4 以降は使いながら優先度を見直す。

| リリース | 名称 | ゴール | 動作環境 |
|---|---|---|---|
| **R0** | ローカル開発環境と API 検証 | Docker 上の Supabase と Web アプリがローカルで起動する。Meta API から自分のデータが取れることを確認する | ローカル |
| **R1** | 収集基盤 | アカウント・投稿・ストーリーズのデータが DB に貯まり続ける。収集の状態を画面で確認できる | ローカル |
| **R2** | クラウド稼働 | PC の電源に関係なく 24 時間収集が続く。ログインして外から画面を見られる | Supabase Cloud ＋ Vercel ＋ 定期実行基盤 |
| **R3** | 基本分析 | 概要、投稿一覧、投稿の伸び方（初速）、期間比較が見られる | クラウド |
| **R4** | 動画分析 | リールの長さ・カット数などを自動で抽出し、視聴時間などの指標と掛け合わせて分析できる | クラウド |
| **R5** | 投稿分類とストーリーズ・オーディエンス | 投稿に独自タグを付けて比較できる。ストーリーズの離脱ファネルとフォロワー属性が見られる | クラウド |
| **R6** | レポートと伸びた投稿の検出 | 月次レポートを自動生成できる。普段より伸びた投稿を自動で知らせる | クラウド |
| R7 以降 | 候補 | AI による画像・動画・キャプションの構造化、競合比較、メンション・タグ付け投稿、ハッシュタグ定点観測 | 使いながら判断 |

**R2 を早めに置く理由。** ローカルだけで収集していると、PC が止まっている間のストーリーズと投稿直後のデータが永久に失われる。画面づくり（R3）より先に、収集を 24 時間動かす方を優先する。

**動画分析を R4 に置く理由。** 自分のリールの動画 URL は API からいつでも取り直せる。そのため動画解析は後から過去分をまとめて実行でき、急ぐ必要がない。一方で視聴時間などのインサイトは R1 から保存を始めるので、R4 の時点で過去のリールも分析対象になる。

## 4. 機能要件

ID の先頭は分類を表す。F-SYS はシステム共通、F-COL は収集、F-UI は画面、F-VID は動画分析、F-RPT はレポート。

### 4.1 R0: ローカル開発環境と API 検証

| ID | 要件 |
|---|---|
| F-SYS-01 | Supabase CLI で、Supabase 一式（Postgres、Auth、Storage、Studio）をローカルの Docker 上で起動できる |
| F-SYS-02 | DB スキーマはマイグレーションファイルで管理する。ローカルとクラウドに同じ手順で適用できる |
| F-SYS-03 | Web アプリ（Next.js を想定）がローカルで起動し、ローカルの Supabase に接続できる |
| F-SYS-04 | 収集ワーカーを Docker コンテナとしてローカルで実行できる。コンテナには動画解析用の ffmpeg を含める |
| F-SYS-05 | 設定値（Meta アプリの ID と秘密鍵、Graph API のバージョン、Supabase の接続情報）は環境変数で与える。秘密情報はリポジトリに含めない |
| F-SYS-06 | README に、環境構築からローカル起動までの手順を記載する |
| F-COL-00 | API 検証スクリプトで、Claude 調査 3.6 章の未確認事項を実機で確かめ、結果を `doc/` に記録する。対象は、フォロワー数の日次推移と時間帯別オンライン数が取れるか、日次指標を一度に何日分取れるか、日付の区切りのタイムゾーン、リールで profile_visits と follows が返るか |

### 4.2 R1: 収集基盤

**アカウント接続**

| ID | 要件 |
|---|---|
| F-COL-01 | Facebook Login で Meta と接続し、対象の Instagram プロアカウントを登録できる |
| F-COL-02 | アクセストークンはサーバー側だけで保持し、ブラウザには渡さない。トークンの有効期限と権限を記録する |
| F-COL-03 | トークンが失効または権限不足になったら、収集を止めずに状態を記録し、画面で再接続を促す |

**収集ジョブ**（取得頻度は 5.2 章）

| ID | 要件 |
|---|---|
| F-COL-10 | プロフィール（フォロワー数、フォロー数、投稿数など）を毎日保存する |
| F-COL-11 | アカウントの日次指標（reach、views、accounts_engaged、total_interactions、likes、comments、shares、saves、reposts、follows_and_unfollows、profile_links_taps）を、内訳（フォロワーか非フォロワーか、投稿の種類、ボタンの種類）とともに毎日保存する。直近 3 日分は毎回取り直して上書きする |
| F-COL-12 | 初回接続時に、アカウント日次指標を API で取れる限り（90 日）さかのぼって取り込む |
| F-COL-13 | 投稿一覧を同期し、新しい投稿を検出する。キャプション、種類、投稿日時、URL などのメタ情報を保存する |
| F-COL-14 | 初回接続時に、既存投稿すべての現時点の累計指標を 1 回取り込む |
| F-COL-15 | 投稿ごとの指標を、投稿からの経過時間に応じたスケジュールでスナップショット保存する（5.2 章） |
| F-COL-16 | 公開中のストーリーズを 1 時間ごとに取得し、指標を保存する。消える直前の値を確定値とする |
| F-COL-17 | サムネイル画像を Storage に保存する（API の画像 URL は期限切れになるため） |
| F-COL-18 | API のレスポンスを加工前の形のまま保存する。API バージョンと取得時刻を一緒に記録する |
| F-COL-19 | ジョブの実行結果（開始・終了時刻、成否、取得件数、エラー内容、レート制限の残量）を記録する |
| F-COL-20 | 同じジョブを 2 回実行しても、データが重複したり壊れたりしない |
| F-COL-21 | API エラー時は、待ち時間を段階的に延ばして再試行する。レート制限に近づいたら取得を控える |
| F-COL-22 | 取得できなかったデータは 0 ではなく「欠損」として保存する |

**画面（最小限）**

| ID | 要件 |
|---|---|
| F-UI-01 | 接続状態の画面。アカウント、トークンの有効期限、権限、最終収集時刻を表示する |
| F-UI-02 | 収集ログの画面。ジョブごとの直近の実行結果とエラーを表示する |
| F-UI-03 | 投稿の簡易一覧。サムネイル、種類、投稿日時、最新の主要指標を表示する（R3 で本格化する） |

### 4.3 R2: クラウド稼働

| ID | 要件 |
|---|---|
| F-SYS-10 | Supabase Cloud のプロジェクトにマイグレーションを適用し、本番 DB として使う |
| F-SYS-11 | Web アプリを Vercel（または同等の無料サービス）にデプロイする |
| F-SYS-12 | 収集ワーカーを定期実行基盤（GitHub Actions を第一候補とする。6.3 章）で動かす |
| F-SYS-13 | 画面にログインを必須にする（Supabase Auth。利用者は本人のみ）。DB は行レベルセキュリティで保護する |
| F-SYS-14 | 収集が一定時間止まった場合や、トークンの期限が近い場合に、メールなどで通知する |
| F-SYS-15 | ローカルで R1 期間中に貯めたデータを、必要ならクラウドの DB へ移せる手順を用意する |

### 4.4 R3: 基本分析

**派生指標**（定義は 7 章）

| ID | 要件 |
|---|---|
| F-UI-10 | 派生指標（保存率、シェア率、いいね率、エンゲージメント率、プロフィール遷移率、フォロー転換率、非フォロワーリーチ比率など）を計算して表示する |
| F-UI-11 | 率を表示するときは、分母（リーチ、閲覧数、フォロワー数）を明示する。エンゲージメント率は分母を切り替えられる |

**画面**

| ID | 画面 | 内容 |
|---|---|---|
| F-UI-20 | 概要 | ファネル（リーチ → 反応 → プロフィール訪問 → フォロー → リンクタップ）、主要指標のタイルと前期間比、フォロワー数とリーチの日次推移グラフ（投稿日を重ねて表示） |
| F-UI-21 | 投稿一覧 | サムネイル、種類（フィード、カルーセル、リール）、投稿日時、主要指標と派生指標。並べ替えと絞り込み |
| F-UI-22 | 投稿詳細 | 投稿後の伸び方のグラフ（1 時間〜90 日）。同じ種類の投稿の中央値との比較。投稿単位のファネル |
| F-UI-23 | 期間比較 | 任意の 2 期間を比べる。プリセットは前 7 日、前 30 日、前月、前年同月 |
| F-UI-24 | 比較の基準値 | 平均だけでなく中央値、上位 25%、下位 25% を表示する（一部のバズ投稿に引っ張られないため） |
| F-UI-25 | 指標変更の注記 | 2025-04-21 の views への統一など、定義が変わった日をグラフと表に注記する |
| F-UI-26 | 最終更新時刻 | どの数値がいつ時点のものかを表示する |
| F-UI-27 | CSV 出力 | 投稿一覧と日次指標を CSV で出力する |
| F-UI-28 | 特殊な投稿の扱い | コラボ投稿、お試しリール、ブースト投稿を区別し、集計から除外できる |

### 4.5 R4: 動画分析

**動画特徴量の抽出**

| ID | 要件 |
|---|---|
| F-VID-01 | リールとフィード動画について、API から動画 URL を取得し、一時ファイルにダウンロードして解析する。解析後は動画ファイルを削除する（動画そのものは保存しない） |
| F-VID-02 | ffprobe で基本情報を取り出して保存する。対象は長さ（秒）、幅と高さ、縦横比、フレームレート、ビットレート、ファイルサイズ、音声の有無 |
| F-VID-03 | ffmpeg のシーン検出で、画面の大きな切り替わりを検出する。切り替わり回数、切り替わった時刻の一覧、平均シーン長、冒頭 3 秒の切り替わり回数、最初の切り替わりまでの秒数を保存する |
| F-VID-04 | シーン検出のしきい値と解析プログラムのバージョンを、結果と一緒に保存する。しきい値を変えて再解析できる |
| F-VID-05 | 新しいリールは投稿の検出後に自動で解析する。既存のリールは R4 リリース時にまとめて解析する |
| F-VID-06 | 動画 URL が取れない投稿（著作権の判定を受けたものなど）や解析に失敗した投稿は、状態を記録して処理を続ける |

「切り替わり回数」は編集上のカット数と完全には一致しない。フェード、ズーム、激しい動きでも反応するため、画面上は「大きな画面変化の回数」として扱う（ChatGPT 調査の指摘）。

**動画の分析画面**

| ID | 要件 |
|---|---|
| F-VID-10 | リール一覧に、動画特徴量（長さ、切り替わり回数、平均シーン長、冒頭 3 秒の切り替わり回数）とインサイト（閲覧数、リーチ、平均視聴時間、視聴維持率、スキップ率、シェア率、保存率、フォロー数）を並べて表示する |
| F-VID-11 | 視聴維持率（平均視聴時間 ÷ 動画の長さ）を計算する。これは動画の長さを自前で持って初めて出せる指標である |
| F-VID-12 | 動画特徴量を区分に分け（例: 長さ 0〜15 秒、15〜30 秒、30〜60 秒、60 秒超）、区分ごとの指標の中央値を比べる |
| F-VID-13 | 2 つの値の関係を散布図で見る（例: 長さと視聴維持率、冒頭 3 秒の切り替わり回数とスキップ率） |
| F-VID-14 | 投稿詳細画面に、シーンの切り替わり時刻をタイムラインで表示する |

件数が少ないうちは統計的な結論を出せない。区分ごとの件数を必ず表示し、件数が少ない区分は目立たない表示にする。

### 4.6 R5: 投稿分類、ストーリーズ、オーディエンス

| ID | 要件 |
|---|---|
| F-UI-30 | 投稿に独自タグを付けられる。タグの軸は利用者が定義できる（例: テーマ、目的、CTA、キャンペーン）。1 投稿あたり 3〜5 個程度を想定 |
| F-UI-31 | タグごと、種類ごとに指標の中央値を比べる（例: 「イベント告知はリーチは低いが保存率が高い」を確かめられる） |
| F-UI-32 | 自分の投稿で使ったハッシュタグをキャプションから抽出し、ハッシュタグごとの成果を集計する |
| F-UI-40 | ストーリーズ画面。日ごとのストーリーズの並びと、1 枚ごとの閲覧数の減り方（離脱ファネル）を表示する。次へ、戻る、離脱、次のアカウントへの内訳とリンククリックも表示する |
| F-COL-30 | フォロワー属性（年齢、性別、国、都市）と反応したユーザーの属性を週 1 回保存する |
| F-COL-31 | 時間帯別のオンラインフォロワー数を、取得できる場合は週 1 回保存する（R0 の検証結果による） |
| F-UI-41 | オーディエンス画面。属性の構成と推移、曜日×時間のオンラインフォロワー数のヒートマップを表示する |

### 4.7 R6: レポートと伸びた投稿の検出

| ID | 要件 |
|---|---|
| F-RPT-01 | 月次レポートを自動生成する。構成は 9.1 章の型に沿う。出力形式は 11 章 Q5 で決める |
| F-RPT-02 | レポートの末尾に、利用者が考察と翌月の施策を書き込める欄を持つ |
| F-RPT-10 | 伸びた投稿を自動で検出する。直近 20 投稿など、同じ種類の投稿の分布と比べて、シェア率や非フォロワーリーチ比率が大きく外れた投稿に印を付ける |
| F-RPT-11 | 非フォロワーリーチ比率の急な低下（推薦対象から外れた兆候）とフォロワーの急減を検出して通知する |

### 4.8 R7 以降の候補

使いながら必要性を判断する。今は要件として確定しない。

| 候補 | 内容 | 前提 |
|---|---|---|
| AI による構造化 | 画像、動画のフレーム、キャプションから、人物の有無、文字の量、テーマ、冒頭の構成などを自動で付与する。R5 の独自タグの自動化 | LLM の利用料が発生する |
| AI アナリスト | 蓄積したデータを材料に、似た投稿との違いや次の施策を文章で示す | 同上 |
| 動画の詳細解析 | 字幕の有無、人物が登場するまでの秒数、音声の音量、話し声と音楽の区別 | 同上、または追加の解析ライブラリ |
| 競合比較 | 他のプロアカウントのフォロワー数と投稿の公開指標を毎日記録し、推移と、フォロワー数を分母にしたエンゲージメント率を比べる | 自分のエンゲージメント率とは定義が違うことを明示する |
| メンション・タグ付け投稿 | 他の人が自分をメンション、タグ付けした投稿を集める | Facebook Login 方式が必要 |
| ハッシュタグ定点観測 | 指定したハッシュタグの投稿を定期的に集める | 7 日間で 30 個までという API 制限がある |
| 外部データ連携 | UTM 付きリンクでのサイト流入、広告データ | 別の API が必要 |

## 5. データ要件

### 5.1 保存するデータ

テーブル設計は基本設計で行う。ここでは保存すべきデータのまとまりを定義する。

| データ | 内容 | 導入 |
|---|---|---|
| アカウント | 対象の Instagram アカウント、接続した Facebook ページ | R1 |

| プロフィールの日次記録 | フォロワー数、フォロー数、投稿数 | R1 |

| 投稿指標のスナップショット | 投稿 ID、取得時刻、投稿からの経過時間、指標一式 | R1 |
| ストーリーズ | ストーリーズ ID、投稿日時、同じ日の中での順番、取得ごとの指標 | R1 |
| API の生レスポンス | エンドポイント、パラメータ、API バージョン、取得時刻、レスポンス本文 | R1 |
| ジョブの実行記録 | 5.4 章 | R1 |
| 指標の定義 | 指標名、意味、単位、使える期間、廃止日と後継の指標 | R1 |
| 動画特徴量 | 5.3 章 | R4 |

指標は「指標名と値」の組で持ち、新しい指標が増えても列を追加せずに保存できるようにする。Postgres の JSON 型の列に指標一式を入れる方式と、1 行 1 指標の縦持ちの方式がある。どちらにするかは基本設計で決める。

### 5.2 収集スケジュール

両調査の提案を統合した。

| 対象 | 頻度 | 備考 |
|---|---|---|
| プロフィール | 1 日 1 回 | 日本時間の早朝 |
| アカウント日次指標 | 1 日 1 回 | 直近 3 日分を毎回取り直して上書きする |
| 投稿一覧の同期 | 1 時間ごと | 新しい投稿を早く見つけるため |
| 投稿指標（投稿後 24 時間まで） | 1 時間ごと | 初速の分析に使う |
| 投稿指標（2〜30 日目） | 1 日 1 回 | |
| 投稿指標（31〜90 日目） | 週 1 回 | |
| 投稿指標（91 日目以降） | 月 1 回 | 投稿数が増えたら頻度を下げるか止める |
| ストーリーズ | 1 時間ごと | 公開中のものすべて |
| 属性データ、時間帯別オンライン数 | 週 1 回 | R5 |
| 動画解析 | 新しいリールの検出時 | R4 |

投稿後の経過時間は、実際に取得した時刻から計算して保存する。スケジュール実行の遅れがあっても、グラフは正しい経過時間で描ける。

## 6. システム構成

### 6.1 構成要素

| 要素 | 役割 | 技術（案） |
|---|---|---|
| Web アプリ | 画面、ログイン、Meta との接続（OAuth） | Next.js（TypeScript） |
| DB | データの保存 | Supabase（Postgres） |
| 認証 | 画面へのログイン | Supabase Auth |
| ファイル保存 | サムネイル画像 | Supabase Storage |
| 収集ワーカー | 定期的に API からデータを取得して保存する。動画を解析する | TypeScript（Node.js）＋ ffmpeg。Docker イメージにまとめる |
| 定期実行 | ワーカーを決まった時刻に動かす | ローカルではコンテナ内のスケジューラ、クラウドでは GitHub Actions を第一候補 |

Web アプリとワーカーを同じ言語（TypeScript）にし、DB アクセスや指標の計算処理を共有する。

### 6.2 ローカル環境（R0〜R1）

```text
Docker
├── Supabase 一式（supabase start で起動）
│     Postgres / Auth / Storage / Studio
└── 収集ワーカー（node + ffmpeg）
        一定間隔でジョブを実行

ホスト（Windows）
└── Next.js 開発サーバー（http://localhost:3000）
```

- Meta アプリは開発モードのまま使う。自分が管理するアカウントだけを扱う限り、Meta の審査は不要。
- Facebook Login の戻り先に localhost を使えるかは R0 で確認する。

### 6.3 クラウド環境（R2 以降）

```text
Vercel（無料枠）            Supabase Cloud（無料枠）
  Next.js  ───────────────→  Postgres / Auth / Storage
                                     ↑
GitHub Actions（スケジュール実行）      │
  収集ワーカー（Docker イメージ）───────┘
        ↓
  Meta Graph API
```

定期実行基盤の候補と比較。

| 候補 | 利点 | 欠点 |
|---|---|---|
| **GitHub Actions**（第一候補） | ffmpeg を含むワーカーをそのまま動かせる。公開リポジトリなら無料 | 実行が数分〜十数分遅れることがある。非公開リポジトリは月 2,000 分の上限 |
| Supabase の pg_cron ＋ Edge Functions | Supabase の中で完結する | Edge Functions では ffmpeg を動かせない。動画解析だけ別の仕組みが要る |
| Vercel Cron | Web アプリと同じ場所 | 無料枠では 1 日 1 回まで。関数の実行時間に上限がある |
| 自宅の PC や小型サーバーで常時稼働 | 制約がない | 電源や回線の停止でデータが欠ける |

投稿後 1 時間ごとのスナップショットは、数分の遅れがあっても 5.2 章の方式（実際の取得時刻から経過時間を計算する）で吸収できる。

## 7. 指標の定義

Claude 調査 4.4 章をもとに、本ツールで使う定義を決める。定義は DB の指標定義と画面の説明の両方に持たせ、変更したときは版を上げる。

### 7.1 自分の投稿の指標（分母はリーチ）

| 指標 | 計算式 | 目的 |
|---|---|---|
| エンゲージメント率 | (いいね ＋ コメント ＋ 保存 ＋ シェア) ÷ リーチ | 見た人のうち反応した割合。分母は閲覧数、フォロワー数にも切り替えられる |
| いいね率 | いいね ÷ リーチ | Instagram が重視する 3 つの指標の 1 つ |
| シェア率 | シェア ÷ リーチ | 同上。フォロワー外への広がりに効く |
| 保存率 | 保存 ÷ リーチ | 国内で重視される指標。目安 2〜3% |
| コメント率 | コメント ÷ リーチ | |
| プロフィール遷移率 | プロフィール訪問 ÷ リーチ | |
| フォロー転換率 | フォロー ÷ プロフィール訪問 | |
| リーチあたりフォロー率 | フォロー ÷ リーチ | |
| 非フォロワーリーチ比率 | 非フォロワーのリーチ ÷ リーチ | 新しい人に届いているか。アカウント単位で算出 |
| 閲覧数／リーチ | 閲覧数 ÷ リーチ | 同じ人が繰り返し見ている度合い |

### 7.2 動画とストーリーズの指標

| 指標 | 計算式 |
|---|---|
| 視聴維持率 | 平均視聴時間 ÷ 動画の長さ（動画の長さは R4 で自前取得） |
| スキップ率 | API の reels_skip_rate（冒頭 3 秒で離脱した割合） |
| 閲覧あたり視聴時間 | 総視聴時間 ÷ 閲覧数 |
| ストーリーズ完了率 | その日の最後の 1 枚の閲覧数 ÷ 最初の 1 枚の閲覧数 |
| ストーリーズ離脱率 | 離脱（TAP_EXIT）÷ 閲覧数 |
| 次のアカウントへの移動率 | SWIPE_FORWARD ÷ 閲覧数 |

### 7.3 アカウントの指標

| 指標 | 計算式 |
|---|---|
| フォロワー純増 | その日のフォロワー数 − 前日のフォロワー数（プロフィールの日次記録から計算） |
| フォロワー増加率 | 期間中の純増 ÷ 期首のフォロワー数 |
| ホーム率（近似） | フォロワーのリーチ ÷ フォロワー数。国内の定義は「ホームからの閲覧数 ÷ フォロワー数」だが、API では閲覧の流入元が取れないため近似値として扱う |

### 7.4 目安値

保存率 2〜3% のような目安値は、出典と年を付けて画面に表示する。目安値は設定で変更できるようにする。Meta 公式の目安値は存在しない。

## 8. 非機能要件

### 8.1 セキュリティ

| ID | 要件 |
|---|---|
| NF-SEC-01 | Meta のアクセストークンとアプリの秘密鍵はサーバー側だけで扱い、ブラウザに渡さない |
| NF-SEC-02 | クラウド環境の画面はログイン必須にする。利用者は本人だけに限定する |
| NF-SEC-03 | DB のすべてのテーブルに行レベルセキュリティを設定する |
| NF-SEC-04 | 秘密情報は環境変数や各サービスのシークレット機能で管理し、リポジトリに含めない |
| NF-SEC-05 | Meta に要求する権限は、使う機能に必要なものだけにする |

### 8.2 信頼性

| ID | 要件 |
|---|---|
| NF-REL-01 | 1 回の収集の失敗が他の収集を止めない。対象ごと、ジョブごとに独立して処理する |
| NF-REL-02 | 再実行しても結果が変わらない（同じデータは上書きになる） |
| NF-REL-03 | ストーリーズの取り逃しを最小にする。1 時間ごとの取得が 2 回続けて失敗したら通知する |
| NF-REL-04 | API バージョンは設定で固定し、自動で上がらないようにする。Meta のバージョン廃止予定を README に記録する |

### 8.3 容量とコスト

| ID | 要件 |
|---|---|
| NF-CAP-01 | 月額費用 0 円で運用できること（LLM を使う R7 以降は別途判断） |
| NF-CAP-02 | Supabase 無料枠（DB 500MB、ストレージ 1GB）に収まる設計にする。生レスポンスは一定期間（例: 180 日）後に削除するか圧縮する |
| NF-CAP-03 | 動画ファイルは保存しない。サムネイルは縮小して保存する |

概算（月 30 投稿、ストーリーズ 1 日 5 枚の場合。推測値）: 投稿スナップショットは 1 投稿あたり約 60 回で月 1,800 件、ストーリーズは 1 枚あたり最大 24 回で月 3,600 件。1 件 2KB としても月 10MB 程度。生レスポンスを含めても、1〜2 年は無料枠に収まる見込み。R1 の実測値で見直す。

### 8.4 保守性

| ID | 要件 |
|---|---|
| NF-MNT-01 | 指標の追加や廃止に、スキーマ変更なしで対応できる |
| NF-MNT-02 | 派生指標の計算式に版を持たせ、変更前後の値を区別できる |
| NF-MNT-03 | DB スキーマはマイグレーションで管理し、ローカルとクラウドを同じ状態に保つ |
| NF-MNT-04 | 指標の計算処理には単体テストを書く |

### 8.5 使いやすさ

| ID | 要件 |
|---|---|
| NF-UX-01 | 画面の表示で Meta API を呼ばない。DB の値だけを表示し、表示が速く、レート制限も消費しない |
| NF-UX-02 | 数値には最終更新時刻を表示する |
| NF-UX-03 | スマートフォンの画面幅でも主要な画面を閲覧できる |
| NF-UX-04 | 画面の文言は日本語にする |

### 8.6 規約の順守

| ID | 要件 |
|---|---|
| NF-CMP-01 | Meta Platform Terms を守る。データは本人の分析目的にだけ使い、第三者に提供しない |
| NF-CMP-02 | アカウントの接続を解除したら、そのアカウントのデータを削除できる |

## 12. 用語

| 用語 | 意味 |
|---|---|
| プロアカウント | Instagram のビジネスアカウントまたはクリエイターアカウント。API の対象になる |
| リーチ | 投稿やアカウントを見たユニークなアカウント数 |
| 閲覧数（views） | 表示された回数。同じ人の再表示も数える。2025-04 に impressions から置き換わった |
| スナップショット | ある時点の累計値の記録。時系列に並べて伸び方を見る |
| 初速 | 投稿直後（主に 24 時間以内）の伸び方 |
| 非フォロワーリーチ | フォロワー以外に届いたリーチ。推薦（発見タブ、おすすめ）経由の広がりの目安 |
| 視聴維持率 | 平均視聴時間を動画の長さで割った値 |
| スキップ率 | リールを冒頭 3 秒で離脱した割合 |
| シーン検出 | 動画のフレーム間の差分から、画面が大きく変わった箇所を見つける処理 |
| 生レスポンス | API から返ってきたデータを加工しないで保存したもの |
