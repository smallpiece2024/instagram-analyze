## 1. 目的

リールの画面に表示された文字（編集で入れたテロップ、背景の看板やパッケージの文字）を、表示時刻とともに取り、次の分析に使う。

- 投稿詳細のタイムラインに、カットと並べて文字の表示区間と内容を出す（F-VID-30）
- リール一覧と区分比較に、文字の特徴量（最初に文字が出るまでの時間、冒頭 3 秒に文字があるか、文字の表示時間の割合、総文字数）を加え、「冒頭 3 秒に文字があるリールはスキップ率が低いか」のような問いに答える（F-VID-24、F-VID-31）
- 読み取った文字で投稿を検索する（F-VID-32）

対象は自分のアカウントのリールだけ（2026-10-06 時点で 18 本。全投稿は 25 件）。

## 2. AI を使わない代替案と、それでは足りない理由

| 代替案 | 足りない理由 |
|---|---|
| Instagram の API からテロップを取る | API はキャプション（本文）は返すが、動画に焼き込まれたテロップや字幕のデータは返さない（R0 の検証で取れる項目を確かめた。`doc/verification/r0-meta-api-verification.md`） |
| 人が目視で書き起こす | 18 本なら 1 回はできるが、新しいリールのたびに手作業が続く。表示時刻（ミリ秒）まで手で記録するのは現実的でない。F-VID-26「新しいリールは自動で処理する」に反する |
| 文字の有無だけを画像処理で推定する（エッジの密度など） | 文字の内容が取れず、検索（F-VID-32）と総文字数（F-VID-24）ができない |

したがって文字の読み取り（OCR）は必須（要件 8.7.3 の「代替なし」のとおり）。ただし AI-01（使わずに済むところでは使わない）に沿って、**費用のかからないオープンソースの OCR を第 1 候補**にし、精度が足りないときにクラウドの OCR や画像を読める LLM を使う。

## 3. 入力と出力

### 3.1 入力（OCR に渡すもの）

1. 動画: R4 と同じく `media_url` から一時ディレクトリに落とし、解析後に必ず消す（F-VID-21、NF-CAP-03）
2. フレームの取り出し（ffmpeg）: 各カットの直後（`video_cuts.at_ms` + 100 ms 程度）と、一定間隔（既定 500 ms。F-VID-21）。縦長 1080×1920 のまま、または幅 540 に縮小した JPEG（縮小するかは 6 章の比較で決める。縮小すると費用は 1/4 程度になるが、小さい文字が読めなくなる）
3. 間引き（要件 8.7.3 末尾）: 見た目がほぼ同じ連続フレームを除く（縮小した灰色画像の差分、または知覚ハッシュの距離で判定）。この処理は方式によらずワーカーで行う
4. OCR に送るのは自分のリールのフレームだけ（AI-05）。フレームには自分や他の人の顔が写りうる。クラウドに送る方式では、送ったデータの扱い（AI-07）を 4 章の表に記す

### 3.2 出力（保存するもの）

| 保存先 | 内容 | 要件 |
|---|---|---|
| フレームごとの結果（中間） | 文字、確信度、位置（上・中・下）、フレームの時刻（ms） | F-VID-22 |
| `text_segments`（仮） | 同じ文字が続くフレームをまとめた区間: 文字、表示開始 ms、表示終了 ms、位置、確信度 | F-VID-23、5.3 章 |
| 動画ごとの特徴量 | `first_text_ms`、`has_text_in_first_3s`、`text_coverage_ratio`、`total_text_chars`、`ocr_method`、`ocr_version`、`frame_interval_ms` | F-VID-24、5.3 章 |
| AI・OCR の利用記録 | 処理した対象、方式、モデル名、入出力の量（枚数、トークン数）、費用、処理時刻 | 5.1 章、AI-03、AI-04 |

同じ動画を同じ条件（方式、モデル名、プロンプトの版、フレーム間隔）で二度処理しない（F-VID-25、AI-03）。R4 の `current_video_condition()` と同じ考え方で、今の条件を DB の関数に持たせる。

補足。

- Azure AI Vision の Read（OCR）は無料枠が月 5,000 回と大きいが、有料の単価が頁から取れなかった（2026-10-11）。候補を増やしすぎないため、今回は比較に含めない。Google Cloud Vision が無料枠を超えるようなら再検討する

## 5. 月の処理件数と費用の見込み、設定する上限

### 5.1 枚数の見込み

- リールの長さ: R4 で計測した 4 本は 21〜26 秒。30 秒の動画で 500 ms 間隔なら 60 枚、カット直後の分を足して 60〜70 枚。間引き（3.1 の 3）で **1 本あたり 20〜40 枚**になる見込み（未計測。6 章で実際の枚数を記録する）
- リリース時の一括処理: 既存のリール 18 本 → **360〜720 枚**
- 毎月: 投稿の頻度は月 4〜8 本と仮定（収集を始めてからの投稿の間隔で確かめる）→ **月 80〜320 枚**

### 5.2 費用の見込み（1080×1920 のまま送る場合）

| 方式 | 一括（720 枚） | 毎月（320 枚） |
|---|---|---|
| Tesseract、PaddleOCR | 0 円（GitHub Actions は公開リポジトリなので実行時間に費用がかからない） | 0 円 |
| Google Cloud Vision | 0 円（無料枠 1,000 ユニット以内） | 0 円（同） |
| Claude Haiku 5.5 | 約 $0.25（入力 1.94M トークン $0.19 ＋ 出力 1 枚 100 トークンとして $0.04） | 約 $0.11 |
| Claude Sonnet 5.5 | 約 $4.5 | 約 $2.0 |
| Claude Opus 5.5 | 約 $9 | 約 $4 |

幅 540 に縮小すると Claude の費用は約 1/4。Batches API ならさらに半額。

### 5.3 上限（AI-04、F-VID-26）

- 月の処理本数の上限: **30 本**（見込みの 4 倍。超えたら処理を止めて `check-alerts` で通知）
- 月の費用の上限: **Google Cloud Vision の無料枠 1,000 ユニット／月**（有料の領域に入らない。版 0.2 で Google に決めたため、費用の上限は枚数で判定する）。既存 18 本の一括処理が無料枠に収まらない月は、残りを翌月に回す。1 回ごとの枚数（ユニット）を利用記録に書き、画面で月の合計を見られるようにする（9 章「AI・OCR の利用状況」）

## 6. 精度の確かめ方と、実際に試した結果

**版 0.2 の決定（2026-10-11、ユーザー）**: 6.1 の複数の方式の比較は行わない。精度の確認は、採用した Google Cloud Vision について実装の中で行う。

1. 設計の段階 0（鍵が届いてから）: リール 2〜3 本のフレームを `images:annotate` に送り、応答の形（文字、位置、確信度、言語）と日本語のテロップの読み取りを見て、区間にまとめる規則（同じ文字が続く判定、位置の区分）と `TEXT_DETECTION`／`DOCUMENT_TEXT_DETECTION` の選択を決める。ユニットは 100 枚以内
2. 本番に反映した後（完了条件）: 数本について、読み取った文字と表示時刻を目視と比べ、結果をここに書く

6.1 は、後で別の方式を試すことになったときの手順として残す。

### 6.1 手順（行わない。F-VID-20 の元の案）

1. **対象**: 自分のリール 10 本。装飾テロップ（縁取り、影）、手書き風、縦書き、背景の看板やパッケージの文字を含むものを混ぜる（ユーザーが選ぶ。選ばなければ直近 10 本）
2. **フレーム**: 3.1 の手順で取り出す（カット直後 ＋ 500 ms 間隔、間引きあり）。1 本あたりの枚数を記録する
3. **正解**: 各リールのテロップを目視で書き起こす（文字と、表示の開始・終了の秒）。10 本で 1〜2 時間の見込み
4. **読み取り**: Tesseract 5.5、PaddleOCR 3.7.0（mobile と server）、Google Cloud Vision の `DOCUMENT_TEXT_DETECTION`、Claude（Haiku 5.5 と Sonnet 5.5）で同じフレームを読む。Claude には「画面の文字を JSON（文字、位置、テロップか背景か）で返す」と指示する
5. **評価**: (a) 文字の誤り率（CER。正解との編集距離 ÷ 正解の文字数）、(b) テロップの区間の検出率（正解の区間のうち、開始と終了が 1 秒以内で一致した割合）、(c) 1 枚あたりの処理時間、(d) 1 本あたりの費用（API の応答の使用量から）、(e) 背景の文字を分けられるか
6. **記録**: 結果を 6.2 に書く。試行の費用: Google Cloud Vision は無料枠内（10 本 × 40 枚 = 400 ユニット）、Claude は Haiku と Sonnet で合わせて **$3 以内**の見込み

必要なもの: Google Cloud のプロジェクトと Vision API の鍵、Anthropic の API キー（いずれもユーザーが用意し、手元の `.env` に置く。リポジトリに入れない）。Tesseract は手元の PC に導入済み。PaddleOCR は手元の Python 3.13 に `pip install paddlepaddle paddleocr` で入れる。比較用のスクリプトは `scripts/` に置き、使い捨てとしてモジュール分割やテストは求めない。

### 6.2 結果

比較は行わない（版 0.2）。本番での目視の比較の結果は、行った時点でここに書く。

**動作確認（2026-10-11、親。`scripts/ocr-check.mjs`。ユーザーの希望で「比較ではなく、それなりに読めることの確認」として実施）**: 直近のリール 3 本（2026-08-27、09-04、09-18 の投稿。長さ 21〜27 秒）から 1 秒ごとのフレーム 72 枚（元の動画の大きさ 720×1280 のまま。版 0.2 で「1080×1920」と書いたのは誤り）を取り、`TEXT_DETECTION` に送った（72 ユニット）。1 本目は `DOCUMENT_TEXT_DETECTION` でも読んだ（21 ユニット。合計 93 ユニット、無料枠内）。結果の表は `.local/ocr-check/<media_id>/result.md`、フレームは同じ場所の `frames/`（Git 管理外。確認が済んだら消す）。

- **テロップは読める。** 白い文字に黒い縁取り、画面の上から 1/3 あたり、1 行 4〜12 文字のテロップは、3 本とも 1 秒ごとのほぼすべてのフレームで正しく読めた。例: 「区役所向かいの」「あら汁は大椀でたっぷり」「不定期でイベントも開催」「地元で愛される和菓子屋」。親がフレーム 4 枚を目視で突き合わせて一致を確かめた
- **背景の文字も同じ応答に混ざる。** 駅の看板、メニュー、ポスター、カレンダー、商品の箱の文字が読まれ、多いフレームでは 99〜125 語になる。API はテロップと背景を区別しないので、位置（このアカウントのテロップはほぼ同じ高さに出る）と文字の大きさ（画面の幅に対する高さ）で分ける規則が設計に要る。ポスターの手書き風の縦書き「かりんとまんじゅう」は一部しか読めなかったが、テロップではないので影響しない
- **テロップが看板と重なると割れる。** 1 本目の 1 秒のフレームで「溝口から徒歩4分」が「MU溝」と「から徒歩4分」に割れた。区間にまとめるときに前後のフレームの文字で補う
- **確信度は `DOCUMENT_TEXT_DETECTION` でだけ返る。** 読めた文字は 2 つの機能で同じ。語の確信度は `TEXT_DETECTION` では 0 のまま、`DOCUMENT_TEXT_DETECTION` ではテロップだけのフレームで 0.96〜1.00、背景の文字が多いフレームで 0.67〜0.91。要件 5.3 章の「読み取りの確信度」を保存するので `DOCUMENT_TEXT_DETECTION` を使う（費用は同じ 1 ユニット）
- 1 本 20〜27 枚を 16 枚ずつの 2 要求で送れた。処理時間は計測していない（設計の段階で計る）

親の判断: Google Cloud Vision はこのアカウントのテロップの読み取りに足りる。

**段階 0 の計測（2026-10-11、親。`scripts/ocr-stage0.mjs`）**: 直近のリール 1 本から 8 枚を `DOCUMENT_TEXT_DETECTION` に送った（8 ユニット）。結果は設計書 11 章（JWT の scope は `cloud-vision` で通る、取り出し 1 枚 77〜133 ms、JPEG 62〜145 KB、8 枚の要求の往復 529 ms、テロップの文字の高さは画面の 3.0〜3.5%）。**段階 2 の手元の実行（2026-10-11、`node-worker-developer`）**: 直近のリール 3 本を `video_text` ジョブで処理した（要求 10 回、73 ユニット。1 本 約 6 秒）。3 本とも `success`。区間は 47〜144 本、総文字数 283〜907 文字、文字の表示割合は 3 本とも 1.0（背景の文字がほぼ常に写っているため。背景を含める決定の帰結で、テロップだけの `caption_*` が差を出す指標になる）。カットが 1 秒ごとのリールでは、1 秒で変わるテロップが 1 フレームにしか写らず「2 フレーム以上」の条件でテロップらしさが偽になったので、条件を 1 フレーム以上に変えた（設計 4.3 節）。

**手動で使ったユニットの合計: 93 ＋ 8 ＋ 73 = 174（2026-10）。** 以後、手元で使った分はここに足す。

**ユーザーの確認（2026-10-11）: これでよい。** 理由は、他の OCR サービスに比べて精度が非常に高いこと、背景の文字を拾うのは人が見ても同じなので、背景を含めた文字の情報量をリールの評価に入れてよいこと。したがって、テロップと背景の区別は必須にしない（要件 4.5.1 章の注記を改めた）。設計では、全部の文字から計算する特徴量を主にし、テロップだけの特徴量（位置と大きさで推定）を併せて持つかを決める。

## 7. 決定と、見直す条件

**決定（2026-10-11、ユーザー）: Google Cloud Vision を採用する。** 複数の方式を比較する時間は、得られる差に見合わない（ユーザーの判断）。

採用の根拠（4 章の事実票から）:

- 日本語は正式対応で、言語ヒントなしで自動判定する
- 月 1,000 ユニットまで無料で、見込みの枚数（月 80〜320 枚、既存の一括 360〜720 枚）は無料枠に収まる（5 章）
- 送った画像を学習に使わず、解析後に消す（AI-07）
- 読み取り専用の API で出力の形が固定されており、プログラムで区間にまとめやすい。ワーカーに Python や大きなモデルを入れる必要がない
- 必要なのは Google Cloud のプロジェクト（請求先の有効化、Vision API の有効化）とサービスアカウントの鍵だけ。鍵は GitHub の Secrets に置き、ワーカーだけが使う（AI-06）

送ったデータの扱いの記録（AI-07。確認日 2026-10-11、出典は Google の Cloud Vision の data-usage の FAQ）: Google は送った画像を Cloud Vision の学習に使わない。解析のために短時間保存し、数時間以内に消す。処理地域は指定しない（指定できるのは us と eu だけで asia はない。データの所在の要件はない）。送るのは自分のリールのフレーム（JPEG）だけで、キャプションや投稿の ID は送らない。フレームには第三者の顔や、看板・メニューの文字（店名や電話番号など）が写りうるが、API から返るのは文字と位置だけで、DB に残すのは切り詰めた語と全文、画像は残さない。

含めなかった方式の扱い:

- Tesseract、PaddleOCR: 装飾されたテロップの精度が未検証のまま。Google の読み取りに不満が出たときの代替として 4 章の事実票を残す
- Claude: テロップと背景の文字の区別が分析に必要と分かったときに検討する（要件 4.5.1 章の注記のとおり、区別が必要かは実装後の結果で判断する）

見直す条件: Google の料金や無料枠の改定、月の処理が 1,000 ユニットを超える見込みになった、装飾されたテロップの読み取りの誤りが分析に影響すると分かった（PaddleOCR か Claude を試す）、テロップと背景の区別が必要になった（Claude を検討する）。
